# Agent precision and recovery

The Agent page now records observed coding attempts, project setup, and recovery state. Existing access modes and the selected model/thinking variant remain authoritative. There is no new overall task, time, or tool-call cap.

Project setup is discovered from approved workspace manifests, including nested package projects, Go, Rust, Python, Maven/Gradle and .NET candidates. Inspection does not execute project commands. A command becomes verified only after a successful host execution at its declared working directory with a saved command log. Source, manifest, runner or runtime changes invalidate that observation. Sandbox execution does not establish host runtime verification. Runtime detection alone does not establish compatibility.

Go, Rust, Java, C#, C/C++, Kotlin, Swift and PHP navigation returns lexical declarations and caller candidates. These are labeled as candidates and do not authorize semantic renames. Selected context reports included and omitted paths. Retrieval checks use independently specified relevant files, rather than treating a large context as complete.

The executor checkpoints individual completed tool results within a batch. Resume preserves those results and discards remaining proposed actions so the model must inspect current state and replan. An interrupted mutating operation with no completion record is blocked from automatic resume. Review its effects before retrying. Checkpoints retain the original model, thinking level, specialty and access mode.

Attempt metadata and final replies are saved separately from renderer history. A request is committed at IPC start, terminal results are committed before clearing the checkpoint, and startup reconciles saved turns with durable attempts. Window reload reconnects active runs, pending approvals, clarification, Stop controls and terminal delivery. An application restart records unfinished attempts as interrupted. A result written immediately before a crash can still recover when its completion metadata was not yet committed.

The toolbar scorecard displays observed first-attempt verification, comparable repeat consistency, resumed-run verification, previously passing command regressions, unsupported-claim warnings and per-tool waits. Cancelled/interrupted attempts do not enter success-rate denominators. Unknown tool durations are omitted from timing averages. False-completion rate remains unmeasured until independent outcome grading exists. These records are operational observations, not a benchmark of model superiority.

Progress policy requests concise goal acknowledgment, deliberation before selecting tools, reuse of fresh evidence and grouped reads. Completed updates are audited against recorded checks, numeric check summaries and current requirement coverage. This cannot guarantee every model statement is correct. Reasoning summaries and produced updates remain separate in the UI.

The October 3 live-task fixes validate tool arguments and requirement links before paying for planning or executing an action. The current execution map and its exact IDs are supplied automatically. Acceptance plans are reused until requirements or clarification change. Check reviews retain per-criterion coverage; unchanged proposals reuse their review until source hashes change. Command coverage is reviewed after actual execution, using recorded output and exit codes, so a reviewer cannot demand results before allowing the command to run. Print-only checks still cannot establish behavior.

Preservation, workspace scope and final reporting are separate observations. Before effects, the executor retains indexed workspace hashes. Finalization compares those hashes and recorded before/after changes, and reviews the actual written reply with actual command results. Excluded or unindexed files and effects outside the workspace remain unobserved; this is not a global proof of no writes. Report coverage requires an exact supporting excerpt in the actual delivered reply. Removing an unsupported statement keeps unrelated source evidence; changing the supporting reporting excerpt invalidates only its delivery coverage. Completion proofs group all covered criteria by requirement and phase, preventing later criteria from overwriting earlier ones. A compound check action can complete from combined current evidence for every linked requirement. Command proposals rejected before execution have no exit code. Provisional text is held until coherent claim checks finish. Linked actions complete from validated evidence and satisfied dependencies, including a matched nonzero bug reproduction; baseline evidence never verifies post-change behavior. Automatic checks reuse equivalent fresh `npm test` and `npm run test` results.

When a guessed test-reporter fragment fails to match a real nonzero baseline, an independent review can establish reproduction only from a concrete actual failure tied to the reported bug and source. An unrelated dependency or runner error remains unresolved. This avoids repeating a correct reproducer merely to match presentation formatting.

Execution counts use distinct captured command-log IDs, not source fingerprints. Multiple criterion proofs may refer to one execution; two runs against unchanged files still have separate logs. Declined checks are not executions. Markdown table escaping of command pipes does not turn a real observed command into an unsupported claim. Corrected replies retain exact independently reviewed reporting excerpts so a valid paraphrase does not erase delivery evidence.

Validation: `npm run check:agent`, `npm run check:agent:ui`, and `npm run build`. Automated model fixtures exercise real file edits, host commands, restart/resume and actual React/browser flows. They do not prove a configured provider will reliably follow the policy in live conversations. Live provider acceptance, independent outcome grading and production performance measurement remain separate release criteria.
