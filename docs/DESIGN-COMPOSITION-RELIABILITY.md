# Website composition checks

The layout comparison is a bounded guard against substantial repetition in the supplied recent samples. It does not guarantee universal uniqueness or change the provider model's sampling behavior.

## Construction decision

- A concrete repeated expressive hero or page arrangement can hold construction. Generic alignment, familiar navigation, shared subject matter and required content alone are insufficient grounds for rejection.
- A confirmed rejection remains unresolved through changed proposal wording, malformed responses, provider failures, exhausted comparison budgets and task reopening. A changed recent-design list does not erase it.
- A confirmed distinct candidate clears the hold. Reusing a cached rejected candidate restores its rejection.
- Approval belongs to that candidate. After any confirmed rejection, a different proposal needs its own successful comparison; approval of another candidate cannot make a later failed comparison safe. Rejected relationships remain comparison evidence throughout the task.
- The existing three-comparison budget remains. Exhaustion with an unresolved rejection stops construction with an explanation; it does not silently approve a layout or start an unlimited retry loop.
- With no confirmed rejection, an unavailable comparison still permits construction, explicitly unverified. A first project needs no comparison call.
- None, repairs, faithful recreation and explicit comparison opt-outs do not inherit these holds. Other workspace and verification rules still apply.

Existing task snapshots retain the unresolved rejection and its sanitized comparison reference. They do not include another task's chat, images, assets or project files. Version-2 snapshots remain readable; version 3 records the persistent decision separately from the latest comparison response.

## Rendered result

The existing independent visual review receives prior rejected spatial relationships alongside the accepted storyboard, current screenshots and bounded observed DOM geometry. It checks whether construction returned to the rejected arrangement. A repeated expressive hero can require a targeted originality revision even if supporting sections differ. Harmless implementation adaptations and ordinary conventions do not establish repetition.

This uses the existing review and revision allowance. There is no new review stage, layout menu, template, originality database or temperature override. MAX's motion coverage does not prescribe where its scenes belong.

The DOM probe distinguishes structured HTML visuals from long introductory copy and wrapped action groups. These remain coarse observations for visual review, not an automatic duplication verdict.

MAX's hero guidance now asks for a recognizable subject, one visual lead and a deliberate headline/artwork/action/empty-space relationship before effects. The existing first useful preview can assess that silhouette without adding a checkpoint or capture allowance. No replacement hero geometry is prescribed and previous screenshots are not automatically attached to the builder. Negative references are not sources for invented sample data or assets; requested fidelity still takes precedence.

Proposal comparison and the existing visual reviewer share an evidence instruction: normalize away panel borders, viewport-sized SVG containers and concept labels when assessing repeated expressive relationships. A graphic can technically fill the viewport while still reading as a familiar text/action stack beside a focal object. Ordinary two-column alignment alone remains insufficient for rejection. Observed evidence takes precedence over a contradictory reference description; missing evidence is not proof of distinction. These are model instructions, not a new deterministic visual classifier or a guarantee of compliance.

When refreshing after an edit, prefer an existing sequence with observed changes over a later single-frame end-state check. Re-run the sequence on current source within the existing freshness allowance; do not reuse stale motion evidence or replay form submissions. The GSAP guide also covers independent pixel/percentage transforms that can leave text outside a clipping mask.

## Validation

New standalone hero requests now use the existing layout brief and shared recent-design comparison on both native and direct execution, including requests that say “hero” without “website” but explicitly name a standalone, section, component or other web/brand context. Fictional characters and backend models named Hero do not acquire this workflow. A hero remains a hero: the guard does not add whole-site section counts or required full-site libraries. Ordinary bounded sections, asset/animation-only work, repairs, fidelity, Plan, None and explicit comparison opt-outs retain their exclusions. Startup guidance describes the hero brief requirement before construction, and the existing comparison and revision budgets are unchanged. Live repeat tests must use one task-memory store across fresh tasks and verify that the second task actually receives the first record; isolated histories cannot establish cross-run prevention.

Run the focused composition, profile, None, skill-selection and review checks. These exercise instruction delivery and decisions, including simulated provider failure; they do not establish generated aesthetic quality.

`scripts/test_layout_diversity_live.cjs` runs isolated raw OpenCode, None and MAX builds with the same brief/model/reasoning level. It uses the application's official configured provider-auth handoff and freezes Electron plus shared runtime sources for reproducibility. `scripts/inspect_layout_diversity.cjs` captures desktop/mobile pages and coarse structural cues. Inspect the resulting images and primary interaction before reporting visual outcomes. Raw retains Orvix's security and preview bridge, so it is not a bare provider API experiment. Sampling remains provider-controlled.

Record actual generation duration, provider failures, technical failures and observed visual weaknesses separately. A passing routing check or a distinct proposal cannot establish that a finished website is visually distinct.
