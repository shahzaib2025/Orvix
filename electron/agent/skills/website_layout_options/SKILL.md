# Website layout options

Resolve a design, not just an attractive description. Invent the composition directly from the human's subject, audience, content, primary action, and constraints. This skill supplies decision questions—never a menu of templates, named archetypes, section sequences, or decorative motifs. It does not upgrade the selected profile, require research calls, add a critic pass, or ask permission for ordinary creative choices.

## Scope and grounding

For an open new website or standalone hero, develop two credible directions in the same planning pass, compare them, and detail only the selected one. A planning-only request ends with the options and blueprint in chat: do not create website files, start a preview server, install libraries, or test unbuilt behavior. Repairs, additions, explicit layouts, and faithful recreations preserve their requested identity; do not run an unsolicited competition. Under **None**, apply this workflow only when the human explicitly requests this named skill.

Keep the human's original requirements intact. Unknown business details remain unknown; explicitly identify assumptions and illustrative content instead of inventing awards, client lists, team size, statistics, contacts, or social proof. Do not pad a page with empty future sections (such as placeholder award strips or unsupported metrics); merge thin content or invent a useful explanatory composition instead. Frame viewport fit as a design intention until rendered and measured, and never claim assets exist, animations are verified, or a layout is guaranteed unique without direct observation.

## Develop two compact, genuinely different options

Write **Option A** and **Option B** with comparable conviction and the same human requirements. Both must be viable and buildable—never make one a strawman. Keep each option compact enough to scan and compare inside Orvix's existing cards; reserve the deep spatial and section-by-section engineering for the selected blueprint. For standalone hero requests, scope both options strictly to the hero.

For an ordinary full-site comparison, aim for 100–160 words per option in one or two useful paragraphs; expand when the human explicitly requests detailed alternatives. Cover the decisions naturally rather than printing five mini-specifications under repeated headings. Spend the remaining response budget on the selected blueprint. Do not print an estimated word count as if it were measured.

Treat the following decisions as a completeness check, not a rigid worksheet. Do not print internal subheadings inside each option unless expanded alternatives were requested. Give the central idea and visitor payoff, then describe the first-screen composition through the headline, action, focal subject, relative scale and position. The static screen must work before motion starts; a clever title or a familiar text-and-card arrangement is not a concept by itself.

Include one meaningful interaction as a concise cause-and-effect moment: visitor trigger, visible response and purpose. Honor an intentionally static brief. For MAX, summarize the core motion idea here and develop its full coverage only in the selected blueprint. Briefly identify the page rhythm and visual material, including a plausible source and fallback without claiming unobserved asset availability. Close with the main trade-off and mobile shift. Stacking is valid when it preserves hierarchy, useful media and reachable controls; resolve both alternatives for narrow screens rather than leaving one deliberately unusable. These are five decisions to convey in the short summary, not five sections to expand per card.

Before selection, make the actual structural and conceptual difference between A and B explicit as the opening sentence of **Selection reason**. Changing copy, palette, typeface, decorative shapes, or animation on the same underlying headline, action, and media arrangement is insufficient. If both options collapse into the same geometry, rethink one within this pass. Do not emit a separate structural-difference paragraph between Option B and Selected option; the existing card parser would attach it to Option B.

Compare the two first-screen silhouettes with the visual medium and style mentally removed. Replacing a photograph with an SVG or room diagram in the same position beside the same headline/action stack does not establish a structural alternative. The difference sentence must name a changed spatial relationship or reading path, not just different media or concept labels. Keep useful conventions available; this is a comparison of these two candidates, not a universal ban on any arrangement.

## Public order and selection

Keep the response order card-friendly so Orvix's parser and human readers see the comparison before the detailed blueprint:

1. **Option A** (one or two short paragraphs)
2. **Option B** (one or two short paragraphs)
3. **Selected option: A/B**
4. **Selection reason:** Start with one sentence stating the structural and conceptual difference between A and B. Then compare subject fit, visitor clarity, visual hierarchy, structural distinctiveness, media plausibility, mobile behavior, and feasible execution. Point to a concrete advantage and name the trade-off accepted. Do not use numerical scores or select an option just for novelty or effect count.
5. **Selected layout blueprint** (full implementation plan for the chosen concept only)

Use the explicit A/B labels and selection wording so Orvix can display the existing comparison cards correctly. Keep option summaries as card content; put the structural comparison in Selection reason, outside both cards.

Write these public deliverables directly in your visible assistant response as you develop them: Option A, Option B, the selection reason, then the selected blueprint. Orvix streams this text into its option cards and viewer. Do not keep the whole deliverable only in reasoning or tool arguments and reveal it afterward. This is the existing planning pass, not another model call or approval stage. Submit the compact construction brief afterward when construction is authorized; its comparison result determines construction status, not the streamed draft.

### Select on the actual brief

Develop both candidates before settling on a winner. A/B are presentation labels, not a preferred candidate and an afterthought. Both must satisfy the human's constraints and the applicable profile; repair a deficient proposal in this pass rather than selecting against a knowingly weak version of it.

Theme and quality adjectives do not establish the winning geometry or medium. Photography, diagrams, typography, interfaces and authored scenes can each express craft. Do not assume that a premium white site must feel calm, use a particular font genre or favor photography; do not dismiss an explanatory composition as inherently cold or treat unfamiliar media as automatically harder. Compare the specific candidate's hierarchy, visitor task and available evidence. Asset quality and feasibility are unknown until observed; a fallback is a proposed solution, not a guaranteed finished asset.

Name the audience question or action that the winning composition serves better, and the concrete spatial or interactive relationship responsible. A generic claim that it looks more premium, is warmer, or has easier mobile behavior is insufficient. Preserve the chosen idea when refining it instead of merging both into a familiar generic arrangement. Neither novelty alone nor always choosing B is a solution.

When the existing construction workflow supplies sanitized recent-design notes, compare the selected composition with those relationships as well as with its current alternative. A different Option B does not make a repeated Option A original. Use only the existing bounded comparison; add no history store, layout rotation menu, extra model call or approval step. Without recent evidence, do not promise cross-run uniqueness.

## Selected layout blueprint

Expand only the winning direction into a concrete build plan:

- **First-viewport resolution:** Define desktop and mobile composition, headline wrapping, focal media crop, relationship to navigation chrome, and intended action visibility using proportional relationships and sensible size ranges rather than arbitrary exact pixel guesses. An optional small text wireframe may clarify non-standard geometry; invent it for this design rather than reusing a boilerplate.
- **Section-by-section plan:** For every planned section, match the stated section count and state its visitor purpose, concrete text/media/control placement and relative scale, principal visual subject, and connection to adjacent sections. Section titles like *About*, *Work*, or *Contact* alone are not compositions.
- **Motion choreography:** Where motion changes a section, specify what moves relative to what, what meaning or information the change carries, the readable settled state, and reverse-scroll behavior. For **MAX**, establish its required animated hero and supporting page-wide motion coverage here; remove or redesign effects that lack a clear content role. For pinned scenes, account for entry, progression, release, clearance beneath measured navigation, and natural-flow mobile/reduced-motion behavior. Never pass moving visuals through reading text unless legibility is preserved throughout. **Default** and **Medium** do not inherit MAX's motion stack or pins.
- **Continuity and resilience:** Distinguish literal DOM persistence (elements that travel across sections) from visual echoes (shared alignment axes, proportions, or motifs). Resolve mobile reading order and unavailable-media fallbacks. Keep business facts consistent across both options and the blueprint. Finish every sentence cleanly without truncation.

Before handing off, reconcile the selected blueprint with the selected profile in this same planning pass. For a qualifying MAX website, make its existing requirements observable in the relevant section descriptions: developed content depth, sustained hero artwork, expressive text/SVG moments, the connected multi-section story and distinct pinned experiences where applicable. Take counts and exceptions from the current MAX skill; do not silently substitute a lighter policy because the concept is restrained. A repeated closing CTA is not another developed content purpose, and a highlighted process line alone is not a substantial storytelling scene. Keep important text, media and controls available through reverse scrolling; do not specify resetting readable content to hidden states as the default. This is a consistency check within the existing blueprint, not another critic or review loop.

In that same pass, check that the chosen hero's headline/action/media relationships agree between its option summary and blueprint. If refining the geometry changes those relationships, update the summary too. Count developed content rows separately from navigation and footer; do not announce a count that includes an explicitly excluded footer.

## Existing construction handoff

For authorized construction, keep the full blueprint in the conversation and pass a complete, compact digest to `set_design_brief` within its 3,000-character limit; never rely on truncation:

- **First 1,500 characters:** Selected option label, core spatial geometry, first-viewport relationships, and page rhythm used by the comparison.
- **Remaining space (up to 3,000 characters):** Concise Option A and Option B summaries, clearly labeling the rejected direction **not for construction**, plus selection reason and responsive/fallback essentials.

Submit one selected brief and build only that direction when authorized. Later construction uses the existing bounded preview to compare the built composition against this plan.
