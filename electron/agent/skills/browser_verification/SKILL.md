# Browser interaction verification

Read this skill when implementing, repairing, or reviewing meaningful browser/Electron renderer behavior, responsive layout, loading/failure states, or a requested user flow. It applies across design profiles, including None. Combine it with bug_repair for a defect and the relevant engineering skill for animation or WebGL. It supplies verification methods, not visual templates, an extra critic, or an automatic testing loop. Honor diagnosis-only and no-code requests.

## 1. Choose the real entrypoint and a bounded check

Inspect the actual project, launch instructions, existing server, and current evidence first. Use the user's requested route: file opening, local HTTP, application navigation, or the relevant authenticated state. Identify the main interaction and its observable outcome. Select the smallest sequence and viewports that resolve the requirement; reuse unchanged current observations. A screenshot of the initial screen does not verify a flow.

Use the existing managed preview tools where available. For plain HTML/CSS/JS, start_preview_server with command:"static" uses Orvix's bundled server; use its returned URL instead of guessing a port or installing Python. For frameworks, inspect the manifest and use the existing dev command. Identify an existing process and project before reusing or stopping a server. Skill reads do not authorize extra workspace access, destructive operations, messages, purchases, or production mutations.

Check the actual launch contract. Local ES modules and fetched resources may fail under file:// even when locally vendored. An HTTP preview does not establish double-click compatibility; test the requested route separately and report its limitations. If a browser/tool cannot inspect that route, state that limitation rather than assuming success. Do not disable browser security or silently alter the delivery contract.

For newly delivered or materially changed frontend projects, apply the shared web project launch guidance before reporting completion. Distinguish a page's actual HTTP/build requirement from a preview tool's protocol restrictions. Plain directly openable pages need no batch launcher. Server-dependent Windows projects and newly delivered Three.js scene/model projects need Start-Preview.bat and concise launch instructions. Inspect that user-facing entrypoint when authorized, rather than treating an Orvix-managed preview as proof that the user's launcher works. Keep launch, browser interaction and build evidence separate; no extra verification loop is required.

## 2. Test actions against visible outcomes

Use stable selectors from the real document: semantic roles, accessible names, or established IDs/data attributes. Inspect before guessing. Account for overlays, disabled controls, asynchronous state, and whether the target is uniquely matched. Use state-based waiting when supported; arbitrary long sleeps are not evidence of readiness.

For preview_website, use workflow with an action followed by a changed-state assertion. A workflow assertion uses action:"assert" and a nested assertion with kind, selector where needed, and expected; kind belongs inside assertion, not on the workflow step. The expected field is different from the older top-level assertions text field. Check the current tool definition for supported actions/parameters. Never claim a workflow ran when tool input was rejected.

Prepare one valid bounded preview payload from the actual markup before calling: desktop/mobile viewports, unique primary-action selectors, and (only where useful) one actual motion scene with its changing children. motion.section must match exactly one element; use its real ID rather than a selector spanning several sections. Keep settle_ms between 0 and 500, or omit it for the default. Checkpoints accept progress from -0.1 to 1.1, at most six points and two viewports. Inspect a rejected parameter's explanation and correct that payload once; do not guess a succession of selectors or repeat full-page captures to troubleshoot schema errors. Reuse current successful views and combine affected checks after a correction.

Observe what the user should see after an action: updated content, checked/value state, navigation, validation feedback, opened/closed panel, or a result. A click completing is not proof that its handler produced the expected result. For async operations, inspect loading, resolved success, and relevant failure behavior without unsafe live mutations. Verify reload or reopen only when persistence is required. A displayed confirmation does not establish a backend write; use authorized endpoint/storage evidence where persistence is part of the task. Keep fixtures and live results distinct.

Check relevant keyboard and touch behavior: reachable controls, visible focus, meaningful labels, and no accidental interference with normal typing or page navigation. For dialogs or menus, inspect focus and dismissal when those behaviors are in scope. Do not create an exhaustive accessibility audit for a narrow change; address observed defects and requested requirements.

For responsive navigation, observe closed → open → closed on the narrow layout, including dismissal after following a link when provided. Assert actual visibility, not just `hidden` or `aria-expanded`: author `display:flex`/`grid` rules can override the browser's hidden styling. Closed navigation must uncover content and stop intercepting input. Recheck relevant resize transitions. Preview metrics.hiddenAttributeOverrides identifies hidden elements that still render; resolve an observed override before calling that captured layout passed.

## 3. Inspect layout and state together

Capture the actual requested subject at representative desktop and narrow mobile widths using the tool's viewport controls. Inspect content and controls, not just automated scores. Check document/container bounds, horizontal overflow, clipped or unreachable controls, text wrapping, sticky headers, overlays, and canvas/image sizing. A CSS breakpoint alone does not establish a responsive result. Fix oversized content rather than masking it with global overflow hiding.

When content locks to the screen, include a short desktop viewport within the existing inspection allowance and compare readable content bounds with the actual header and viewport bottom. Reuse preview metrics.viewportFit and motion frames' observations.viewportFit: failures indicate vertical clipping in active fixed/sticky or observable pinned regions. An element's visible flag means partial intersection, not full fitting; fullyVisible reports viewport bounds only and does not prove lack of header/ancestor occlusion. Check readable stages, progression/release and reverse; deliberate decorative or entrance clipping is different from essential copy or controls escaping while locked. A long unpinned section is not a fit failure. Fitting internal scroll panels remain usable; do not add nested scrolling to a cinematic story just to hide excess content. Report the bounded check's limitations, especially custom transform pins without an observable active state; no extra critic, mandatory screenshot count or polishing loop is introduced.

Check that loading, ready, empty, and error states agree with reality. A hidden overlay can still display when author CSS overrides the hidden attribute. Verify actual visibility and whether it blocks pointer or keyboard access; check that successful content is uncovered and failures have truthful feedback. Missing scripts that fail before initialization must not be presented as confirmed success or endless unexplained loading. Inspect console and network errors when the tool provides them, and distinguish preexisting unrelated errors from failures on the changed path.

For animation or scroll behavior, inspect meaningful before/during/after states and reverse/re-entry where relevant within the existing budget. Check reduced motion preserves content and controls. Read scrolltrigger for pin boundaries and refresh issues, and threejs for model framing, render state, geometry, or reset/resize behavior. A moving decorative element does not establish a complete interaction or premium visual quality. Captured checkpoints do not establish continuous smoothness, frame rate, or real-device performance.

Within that same inspection, protect readable headline, body and primary-action space. Inspect the actual screenshot after entrances settle and in the reduced-motion composition: an opened flap, floating image or SVG can cover text even with no overflow and a working button. Read preview readableContent findings for opaque-layer occlusion and clipped text ink; inspect glyph descenders in line-reveal masks rather than assuming a fitting element box means the letters fit. Correct the supported geometry/stacking/mask defect within the existing targeted correction allowance and recheck it. Do not hide essential text or disable the inspection to obtain a pass. These bounded diagnostics do not replace looking at the rendered page, and skipped/in-flight/rotated text is not verified as safe.

When reveals are involved, include a supporting collection or text passage after its entrance settles. Inspect the actual children: a visible section with transparent cards or word spans is still missing content. Use motion observations/workflow selectors on those children; inspect computed opacity through ancestors when a region looks empty. Distinguish intended temporary story states from essential content that never reaches its readable end state. Test a representative short, wide viewport as well as narrow mobile when responsive motion branches differ; check final counters, diagrams and copy even where pinning is disabled. When implementing a reduced-motion listener, also exercise the preference changing during the visit and confirm that text settles visibly and owned loops stop.

For important media, inspect the displayed image and network failures after relevant lazy content enters view. A generic fallback can make brokenImages equal zero while the promised product or subject image is still missing; do not count a substituted placeholder as successful media delivery. Retain direct remote URLs when requested, replace unavailable URLs with suitable permitted sources, or disclose the missing asset. For demo forms, check that the invitation and resulting message agree about whether anything is actually sent.

## 4. Diagnose failures and retain useful evidence

If the flow fails, retain the failing state, relevant browser output, exact trigger, and current source identity; use bug_repair to trace its cause. Inspect tool errors before repeating an operation. Do not restart completed workflows or apply many speculative changes just to obtain a passing screenshot. Fix concrete defects together, then recheck the affected sequence once. After source changes, screenshots/assertions for that state are stale; reuse only evidence for unaffected behavior.

Do not simulate a passing state by editing the DOM or suppressing an error and then report it as the delivered application. Temporary browser changes can isolate a cause, but label them diagnostic, keep them separate from source fixes, and verify the unmodified final artifact afterward. Check the visible result of each meaningful verification operation rather than assuming a tool succeeded.

## 5. Report exactly what was observed

For a requested visual composition or quality assessment, read visual_composition; functional verification alone does not require it. Use the same current captures and bounded workflow rather than adding another model or review loop.

State the route, relevant viewports, action/outcome, actual failures, and material gaps. Distinguish inspected screenshots, asserted user flows, structural checks, builds, persistence checks, and physical device testing. Emulation is not physical mobile acceptance. A passing automated layout/accessibility check does not certify design quality. Reuse evidence IDs and the existing verification reporting; no additional public controls, server, selection gate, or model call is required by this skill. Never report an unavailable, skipped, stale, or rejected check as passed.
